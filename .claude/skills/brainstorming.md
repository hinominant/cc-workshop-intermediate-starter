# Skill: Brainstorming — Spec前段の要件引き出し

**Trigger**: 新規Feature/Epicチケット作成時、Spec作成前

## Purpose

AIがSpecをいきなり書かず、ユーザーと対話して要件を引き出す。
前提が曖昧なまま実装に入ることを防ぐ。

## When to Use

- 新機能の要件が1文程度しか書かれていない
- 「〇〇が欲しい」「〇〇を作って」程度の指示
- 要件に複数解釈がありうる
- 成功基準が不明

## When NOT to Use

- すでに詳細なSpecが存在する
- バグ修正（既存機能の修正）
- 些細な変更（文言修正等）

## The Process

### Step 1: 最低3つの質問

以下の3つは必ず問う:

1. **What**: 何を作りたいか（具体的な挙動）
2. **Why**: なぜそれが必要か（根本の目的）
3. **How verify**: どうやって「できた」と判定するか

### Step 2: 前提の明示

回答を元に、以下を明示する:

```markdown
## 前提（私の理解）
- ユーザーは ...
- 入力は ... を想定
- 出力は ... を想定
- エラー時は ... と想定

## 不明点
- [ ] ...（ユーザーに確認必要）
- [ ] ...

## 複数解釈
解釈A: ...
解釈B: ...
→ 推奨: A（理由: ...）
```

### Step 3: ユーザー承認

上記をユーザーに提示し、承認を得てからSpec作成に進む。

### Step 4: Spec化

承認された内容を `docs/specs/{ticket}_spec.md` に転記:
- Purpose（Whyから）
- Acceptance Criteria（How verifyから）
- Out of Scope（不明点・解釈保留から）

## Anti-patterns

**Bad**: 1文の指示から即Spec作成
```
User: ログイン機能を作って
AI: [spec.md作成] AC: ログインできる, ログアウトできる, ...
```
→ 前提がブラックボックス。後で「そういう意味じゃなかった」が頻発。

**Good**: 質問→前提明示→承認→Spec
```
User: ログイン機能を作って
AI: ログイン機能について確認させてください:
    1. メール/パスワード？SNS認証？両方？
    2. なぜログインが必要？（データ個別化？決済？）
    3. ログイン成功をどう検証しますか？
User: メール/パスワード。ユーザーデータ個別化。
     ダッシュボードに自分のデータだけ表示されればOK
AI: [前提明示 → 承認 → Spec作成]
```
